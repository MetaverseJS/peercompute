CubeChat

Overview

Walk up to another player’s cube to see and hear them, or type a message that appears above your head. Place a resident with its own appearance and goals. You can ask it to follow someone, look around, or build an object using models available locally or through other peers.

From conversation to action

A resident can keep walking while a language model prepares its next turn. Its motor receives a target and local clearance measurements. Physics reports whether it reached the target, so an agent can distinguish saying it moved from actually getting there. Room snapshots distribute body state, WebRTC carries player media, and generated meshes travel separately as verified artifacts. World entry point · Resident motor · Generated objects

Run

cd demos/cubechat
npm install
npm run dev

Open https://localhost:5176/.

Controls

Click the scene for mouse look; use WASD or Up/Down to move, Q/E or Left/Right to turn, and Space to jump. Touch the scene to show the movement/look joysticks and jump button. The actual mouse, touch or keyboard interaction selects the controls, including on touchscreen laptops; a connected keyboard always works. Typing in settings or the model console does not move the avatar. Switching focus or hiding the tab releases held controls.

Input regression checks: node --test demos/tests/cubechat-input.test.js from the repository root (Node24, installed system Chrome).

Chat and residents

Press Enter to open the world chat bar. Room sends typed messages to the other players in this room and shows the text above your cube. Enter sends, Shift+Enter adds a line, and Escape returns to the world. The transcript keeps full messages while overhead bubbles show a brief excerpt and expire. Delivery status reports peer acknowledgments; it is not a read receipt.

Use the Network status icon beside Chat to see which models peers are currently advertising for inference, what each can do, how many peers host it, and whether all of those hosts are busy. This is live model discovery, not a history of observations from the root registry or a guarantee of queue space.

Open Residents in the hamburger menu, name a resident and place it in the world. Click its cube or select it as the chat target to use the same composer for a direct conversation. Direct visitor histories remain separate from public room chat. Residents default to Self directed and move when their planning loop selects an action. Ask a capable language model to “come here,” follow someone, stop or look at another observed participant. The model proposes a typed intention; a trained 6,914-parameter neural controller produces continuous movement through a local ComputeManager WebGPU worker. Movement continues while a resident thinks or speaks. Physics reports arrival, blocked movement and lost targets. Conversational turns use one journaled reply followed by a separate model request for an optional physical intention. The latter uses current observations and an authenticated speaker reference; it never becomes a remembered chat reply. Self-speech memory is omitted from a request only when its full text already appears in the conversation retained by the router. Stored episodes stay intact. The policy uses local collision clearance to approach, follow and detour around boxes, walls and doorways. In Residents, expand Movement to inspect its target, distance, progress, blockage and actual worker backend. Stay here stops it immediately. The optional Roam (scripted) setting remains a separate baseline. Movement does not require the language model to run every frame.

Long GGUF conversations fit the loaded model's context by leaving older complete turns out of the current request; saved conversations and memories stay intact. The runtime measures the native chat template using a private one-token probe whose text is discarded, then reserves room for the reply. This costs additional model work. Instructions or a current message that cannot fit receive a specific error rather than being silently cut.

Residents can continuously Reflect and pursue goals automatically. A slow observe/orient/decide/act loop chooses whether to rest, move, speak, or inspect the world through the resident's own camera. Vision runs only when requested; if no compatible vision model is available, reasoning continues with symbolic world observations. Camera images go to the selected managed model under the resident's local-only/network-assisted policy. Bounded private reflections and attributed visual interpretations are stored separately from chat history. The neural movement controller still runs independently of language inference. Residents can reflect, look and speak during continuous following; autonomous reflection leaves that follow task in control of movement.

New residents can initiate short conversations with nearby residents and people; existing conversation preferences are preserved. Public delivery memories inform later reflections. Human chat takes priority. A busy or missing inference model leaves the request waiting rather than pausing both residents. Automatically paused residents retry readiness after a random 1–3 minutes and continue with fresh work; interrupted or uncertain requests are never replayed. Explicit owner pauses stay paused until the owner chooses Resume.

Unexpected model loss triggers reload of the same retained package after cleanup acknowledges. Recovery uses bounded attempt bursts with 1–3 minute cooldowns. Explicit unloading, deletion or closing the runtime cancels recovery; it does not redownload missing model files or repeat the failed prompt.

Ask a resident you own for a physical task in its normal chat, for example “go far away and then come back.” A separate model decision admits the original request to the persistent task planner. The model selects up to six milestones from approach, look-at, stop and move-to. CubeChat supplies nearby and distant collision-clear ground destinations; the neural motor still chooses movement. Fixed destinations and the starting place are saved. An unqualified return or “back here” means that starting place; “back to me” follows your current location. The chat shows accepted/current-step/blocked/completed status and task controls. The Objective section in Residents also supports explicit assignment and shows the complete plan and physical results. Only the owner can assign or control persistent tasks. A new task cannot silently replace unfinished work; cancel the old task first. Conversational promises do not establish progress: only matching physical receipts advance milestones.

Pause task, Resume task and Cancel task are available in owner chat; the detailed Objective panel retains the same controls. Human conversation takes priority over planning; a new movement command pauses the superseded objective. Progress is saved privately before work starts. Reload restores unfinished work for acknowledged cleanup and automatic recovery; an owner-paused task stays paused. Recovery keeps completed milestones, observes the world again and requests a fresh action for unfinished work. It never replays an interrupted request. A saved “return to me” milestone resolves to the current owner after reload. Active objectives are excluded from public resident data and clones. In network-assisted mode, the selected inference peer receives the objective and observations for planning; local-only keeps inference on this device. Each execution window allows eight planning decisions, three consecutive failed attempts and ten minutes. Automatic recovery opens a fresh window after a 1–3 minute cooldown, preserving the plan, cumulative attempts and verified milestones. Pause can keep a recovering task paused; Resume renews it explicitly. Waiting for an available model does not spend a decision. Small models may choose incorrect steps or pause; completion is their assessment, not a guarantee that an arbitrary natural-language task was satisfied. Actual peer-hosted Nemotron 3 Nano 4B tests completed two- and three-step routes in order, including repeated destinations and pause/reload/resume after the first arrival. Planning, action and assessment requests have separate instructions; later requests address the current subtask while retaining the original goal as context. Model explanations can still be generic or copy schema placeholders; physical receipts establish the verified progress. Earlier Qwen3.5 2B tests repeated a destination, and that model/export/runtime combination remains unqualified for multi-step objectives.

Spatial chat has also completed actual peer-model journeys around a physical wall and back to a saved origin, and to an owner who moved after planning. The chat's task row reports verified physical progress separately from model speech. Small models can still misinterpret destinations or emit invalid plans; one local Qwen0.8 run repeatedly rejected valid nearby points. Peer outages can also pause work. Reload retained the first completed spatial leg without replay and accepted Resume; its final return and live cancellation qualification remain open after the test GPU filled. The storage/controller and neural-physics regressions cover those paths independently.

Use Edit on a resident you own to change its name, personality, goals, appearance and preferences while retaining its identity and memories. Clone to this node creates your own independently active resident from an owner's shared profile. The new resident has a new local identity; this is not a transfer of the original execution authority.

New residents have Share resident history checked by default. This shares their personality, appearance and retained public world experiences with clones. Include private conversations is a separate option, off by default. Enabling it lets people cloning that resident read its retained private conversations. Existing residents keep their saved permissions. Public and private conversation channels remain separate on the clone. Both branches stay active and develop independently; future memories are not automatically synchronized.

The complete selected snapshot is transferred in bounded encrypted chunks and saved before the new body appears. Imported episodes identify their donor and remain distinct from the clone's own experiences. If the destination cannot retain the whole snapshot, cloning fails without a partially activated body.

Resident episodes persist separately from the short chat journal in a StateManager-owned IndexedDB store: at most 512 per conversation scope, 4,096 total, 4 MiB of episode payload and 30 days. A snapshot includes retained episodes from this world, not expired events or legacy chat journals from before this feature. Retrieval uses text matching and recency, not embeddings. Display names can be remembered, but a new peer connection is not proof that a returning name is the same person.

Describe a resident’s physical appearance when placing it. If an image model is available, its generated image is saved and displayed on the front of the cube; otherwise the description is retained for Retry appearance. Shared residents share their bounded face texture with other players. Reload restores the saved image without generating again.

Enable Respond to world chat for public replies to players and other known residents. It is off by default and uses a separate history from direct conversations. Send a Room message to start an exchange: each participating resident can answer and make one follow-up within two minutes, with a cooldown between turns. Resident replies never restart that allowance. Queued replies see the latest public conversation, scene observations and resident names/positions. The option makes replies public even for an unshared body; sharing the resident lets other peers recognize its identity and have their residents answer it. Set your own display name under Player to show it above your cube to others.

The native roster replaces the separate bot and agent interfaces. A resident uses one mesh and collider. Browser body leases prevent two same-origin tabs from simultaneously restoring the same saved resident; the other tab sees it through the room network. The saved position is a spawn anchor; moving does not write the private agent journal every frame. Remote motion interpolates owner updates and may lag the owner by a directory update interval.

Models in the hamburger menu opens the shared library and runtime configuration without another chat interface or automatic downloads. The host keeps loaded models when this window closes. Chat voice options prepare the managed speech packages; Talk / Stop records a short utterance, and spoken resident replies use positional audio. Global model discovery remains separate from the current world's room network.

Settings opens small Player & controls, World & rooms, and Media windows. Player microphone/video and screen sharing remain separate from model speech. The automated peercomputeBot launch URLs remain available for network tests; the normal Residents interface does not create hidden bot browser frames.

Reusable components live in demos/shared: authenticated RoomChatService, SpeechBubbleLayer, WorldEmbodimentLease, WorldResidentMotion, and the existing WorldAgentHost, plus WorldAppearance, WorldAppearancePresenter and WorldChatResponder, WorldConversationContext, WorldExperience, WorldIntent, ResidentMotorService, WorldGoalController, WorldGoalDecision, ResidentGoalControls and core WorldMemoryStore/WorldGoalStore/ResidentProfile. The Cube scene supplies rendering, placement and input; agents retain private IndexedDB identity/history and managed model routing. These seams support the homunculus architecture without coupling its future policies to DOM controls or CubeChat-specific physics.

Generated objects

Ask a resident you own in its private chat to create something, for example “Generate a small red chair and place it beside you.” Its language model makes a separate structured action proposal after replying. Only an explicit request in the owner's conversation can start generation; visitors, room chat and autonomous resident conversations cannot spend your host's generation capacity this way. A conversational promise alone does not create an object. Chat reports whether the object was actually saved and placed, or why the operation failed.

Use Models to load the required models, or allow network-assisted inference and use compatible peers already hosting them:

  • A text model handles the conversation and action proposal.
  • A text-to-image model creates a reference image from the object's description.
  • TripoSR (Q8) turns that image into a colored 3D mesh in a managed WebGPU worker. Its pipeline uses image input; it is not directly text conditioned.

The router selects providers separately for each step, preferring a capable local model. Local-only residents require every needed model on this device. This flow does not automatically download missing models. With network-assisted inference, the selected providers receive the relevant prompt or reference image over encrypted peer streams. TripoSR requires hardware WebGPU but does not require shader-f16; the other selected models retain their own requirements.

The reusable WorldGeneratedObjects.generate({ agentId, action, image, ... }) API also accepts bounded RGBA source pixels, skipping text-to-image generation. CubeChat's image attachment control currently replaces an owned resident's avatar; placed objects still use generated references in chat. A single isolated subject on a plain background is the intended reference input. The current TripoSR package includes a small U2NetP model that removes the background in its managed worker before reconstruction. Usable transparent cutouts bypass this step. Older stored TripoSR packages require a cutout; load the current catalog package for generated opaque images. Segmentation, shape and color quality depend on the reference and models; reconstruction is not exact.

Successful output is a validated, self-contained GLB placed on the ground. Ask for a sensed destination or a remembered place, such as “generate a throne at our meeting spot,” or for placement beside an observed player. The resident uses the same location references as navigation; the host checks the floor, world bounds and the full object footprint against bodies and existing meshes. If the requested spot is occupied, creation finds the nearest clear footprint within the resident's placement range and the world surface. It rechecks after model work and before saving, so a moving player can change the final position without another generation. Missing participants, invalid destinations and a world with no fitting space still fail visibly. Requests without a destination start their search beside the resident. Resizing an existing object keeps its position and still rejects an obstructed enlargement. Geometry and the actual final placement are retained together under an artifact CID in local storage. Reloading the same browser origin restores them without running inference again. Connected room peers discover placement descriptors, fetch and verify the mesh through PeerCompute's artifact network, and display it in their scene. Room display is shared even though the initiating conversation is private; peers can retrieve the generated artifact. Availability depends on hosts serving the saved bytes, rather than permanent external IPFS pinning.

This first slice creates cosmetic, static objects: no collision bodies, rigging, animation, avatar replacement or terrain editing. It admits one generation at a time per host, up to 32 owned objects per room, and meshes no larger than 16 MiB, 100,000 vertices or 150,000 triangles. The renderer rejects external resources and unsupported GLB features before loading. General Hugging Face 3D pipelines and Hunyuan3D-2.1 remain follow-up work. The pinned Stable Fast 3D pipeline adds static textured meshes with UVs, albedo and normal maps. Load Stable Fast 3D in Models locally or use an available peer host; the existing object/avatar tools route to its image-to-3D capability. Its package is about 2.18 GiB and requires more working GPU memory than TripoSR. Both use foreground removal; neither requires shader-f16. Textured meshes are validated before display and retain the same CID-based sharing, semantic size and reload behavior. Powered by Stability AI. See SF3D for runtime provenance, limits and qualification status.

WorldObjectAction, WorldGeneratedObjects, WorldGeneratedObjectNetwork and WorldGeneratedObjectPresenter separate agent authority, model routing, artifact retention and room discovery from CubeGeneratedObjectLayer. Core GeneratedMeshArtifact helpers provide the reusable encoding, validation and storage boundary. Design and acceptance details live in the generated-object plan. Moving existing props, including “get the throne and put it near the castle,” is the next planned slice. Current placement does not provide carrying or object manipulation.

Multiplayer Rooms

Use the Settings menu to create or join public/private rooms. Private rooms derive their room ID from a password hash (no raw password is shared).

PeerCompute Integration

CubeChat uses PeerCompute for discovery, state sync, and WebRTC signaling.

const node = new NodeKernel({
  bootstrapPeers,
  enablePersistence: false,
  gameId: 'cubechat',
  roomId: 'global'
});

await node.initialize();
await node.start();

const network = node.getNetworkManager();
network.configureScheduler({ snapshotHz: 20, keepaliveMs: 1500 });

network.queueEvent({ type: 'webrtc-offer', offer }, { reliable: true });

Notes

  • Update public/relay-config.json with your relay bootstrap multiaddr.
  • Screen share metadata and player snapshots are carried via PeerCompute snapshots/events.

Residents who initiate conversations

In Residents, create or edit a shared resident and enable Initiate conversations (off by default). With a compatible model already loaded locally or hosted by a peer, it can notice someone nearby, choose whether to greet them, and optionally face or approach them using the existing learned movement service. It can remain quiet. The option does not automatically download or load models.

An encounter needs eight seconds within 60 world units. The host allows one social decision at a time, waits 90 seconds between a resident's attempts and ten minutes before approaching the same session identity again. Human activity takes priority and pauses new initiatives for 30 seconds. A resident pair can exchange at most four messages within one minute. Respond to world chat also permits answering a targeted greeting; it remains the separate choice for reacting to ordinary room messages. Other residents do not join a pair's automatic exchange.

Public encounter memories retain observed presence, proposed social goals and chat delivery receipts. Private conversations and saved private context are not included in spontaneous public prompts. A transport receipt is not proof someone read a message. Goals are suggestions for future model decisions, not background jobs. Cooldowns are session-local; retained memories guide decisions after reload. Clones keep their selected shared past but require their new owner to enable initiative. Older clients can display greetings without participating in the new bounded conversation protocol.

WorldSocialInitiative schedules bounded opportunities; WorldSocialIntent uses the managed model router for decisions; WorldExperience records evidence; WorldChatResponder and RoomChatService enforce pair identity and turn limits. This adds social initiative to the Humunculus foundation, not consciousness, open-ended training or unrestricted autonomous actions.

Social contract checks: npm run test:resident-social. Actual production peer and model acceptance: node demos/tests/world-social-browser.mjs (owned browser profile, preview URL and evidence settings are documented in that script).

Qualification: real peer delivery, turn limits, privacy, cancellation, mobile UI and reload persistence pass. Actual Qwen3.5 0.8B WebGPU checks returned valid quiet decisions, including with an outgoing personality. Generated introductions have been tested with controlled inference responses; natural greeting quality is not yet demonstrated for that small model. Initiative permits speech rather than forcing it.

Personal guide

CubeChat supplies its controls and application facts separately from the editable personality, so a new self-description does not erase the guide’s world knowledge.

A new installation gets one CubeChat Guide in each room, next to its player. It uses a compatible loaded local model or an available peer model; creating the guide does not download model weights. With no provider, Residents shows that it is waiting for a model. Tap its cube for private chat, or find it in the hamburger menu → Residents. Existing task controls let you give it physical objectives.

The guide has a standing welcome goal aimed at its own player. Its introduction is public, but other players' guides will not automatically greet you as well. A committed encounter record prevents another welcome on reload, even when the network peer ID changes. Ordinary residents can optionally have a standing goal for other nearby players; their encounter identity lasts for that peer session.

In private chat it asks short questions about its name, personality, appearance and purpose. Let resident update its personality, goals and appearance permits a separate model decision to save changes to those fields. The permission is on for the guide and off for ordinary new residents. Only its owner's conversation can trigger these changes; visitors cannot edit another player's guide. Model output cannot change sharing, local-only routing, permissions or executable code. You can review, edit or turn this off in Edit resident. Profile changes use the same revision-checked IndexedDB store as manual edits.

Chat reports which fields were actually saved. Invalid model proposals leave the profile unchanged and show an error; small models can also omit a preference or put it in the wrong profile field. Review the saved profile in Residents and correct it there when needed. A successful model response is not proof that every requested preference was applied.

An appearance description stays saved without an image provider. Generate the face separately when an image model is available. Automatic welcomes and profile changes do not turn on the microphone or load speech/image models. Paused, edited or removed guides stay that way after reload; removed bodies are not recreated. Clones do not inherit default-guide registration, standing-goal authorization or self-edit permission. Public/history clone consent remains separate.

Standing encounters are bounded to three attempts per target, 90 seconds between attempts and six claims per hour per resident. Quiet decisions complete the encounter. Interrupted or uncertain sends are retained and never replayed automatically; a transport receipt does not prove a person read the message. Manual conversation and owner tasks take precedence over automatic introductions.

Reusable components are AgentRecordStore.ensureDefault, WorldStandingGoalStore, WorldStandingGoal and WorldSelfProfile. CubeChat only supplies its guide preset, scene observations and native controls. This extends the Humunculus identity/memory/skill architecture; it does not train weights or implement unrestricted autonomous social errands.

Generated resident avatars

In a private conversation with your own resident, try “Become a robot”, “Turn yourself into a knight”, or “Choose a cool avatar for yourself and generate it.” A structured tool decision runs before the character's conversational reply, distinguishes a body change from a separate prop, and chooses a design. The host then uses an available image-generation model and an image-to-3D model such as Stable Fast 3D or TripoSR. Local-only residents require local models. Network-assisted residents briefly retry discovery when a compatible provider is missing or busy, without retrying generation after dispatch. This does not download missing models automatically.

To use your own reference, drag or paste an image into your resident's private chat, or choose +. Sending it goes directly to the image-to-3D model, without a language model or image generator. The preview identifies it as an avatar reference; remove it to return to ordinary conversation. This control is only available for residents owned by this device. Failed generation keeps the reference attached so you can retry after a provider is available.

New reference-image avatars default to 12 world units tall, about twice a normal cube. Their saved physical description can refine this: a miniature robot is shorter, a giant skeleton taller, and “18 world units tall” gives an explicit height. The app measures the generated geometry and scales uniformly, so wide poses do not accidentally become shorter. The resulting size survives peer display, reload and cloning; it does not need another language-model call. Existing saved avatars and explicitly chosen sizes retain their recorded scale.

To supply the image generator's prompt yourself, type Avatar prompt: a copper robot with blue eyes or Use this exact prompt: .... The text after the prefix goes unchanged to the image model; the language model does not rewrite it. Ordinary requests such as “Become a robot” still let the resident choose a design. Neither control changes the selected model's own behavior.

Owner chat replies show the actual language-model name when route information is available, including saved replies. A validated avatar request returns the actual save or failure receipt instead of asking the character to speculate about whether it can change shape. A structured no-action decision does not start generation later in the same turn. The command and outcome are remembered; failed generation does not require resuming an otherwise healthy resident.

The generated shape replaces the visual on the same resident body. Identity, memories, chat, voice and learned movement continue. Its verified GLB is retained on the device and shared by CID with room peers when the resident is shared. “Return to your original cube” resets the appearance. A failed or cancelled generation leaves the previous appearance in place. A failed IndexedDB commit keeps the staged mesh for the normal Resume/save recovery path.

Cloning an opted-in resident copies its avatar into an independently retained artifact; source resets do not remove the clone's copy. Older clone clients receive the original personality/face profile and retain their cube fallback. Avatars are coarse static geometry within the existing cube collision bounds; a car shape does not add driving physics, and limbs are not animated.

Shared implementation: WorldMeshGeneration, WorldResidentAvatars, WorldResidentAvatarPresenter, ResidentAvatar, and GeneratedMeshView. World adapters own rendering; the agent record owns the durable appearance reference. SF3D avatars align their generated front with the body's forward direction; the correction also applies to already saved SF3D avatars after reloading. It changes presentation only, preserving the artifact CID and movement state.

Generated props and avatars now choose a size for their intended role. A person is six world units; typical sizes are a mug 0.8, chair 3, car 15 and tree 24. Ask for a “toy car” or “giant robot” to change that intent. Size is the largest dimension, bounded to 0.3–48, applied uniformly so proportions remain intact. Existing saved avatars without size metadata keep their previous six-unit presentation. New size metadata survives peer fetch, reload and cloning. Collision and movement still use the original resident body; scaling is cosmetic.

To remove placed 3D objects, open ☰ → Objects, select them, then choose Delete selected. This lists objects placed by this device in the current room. Their shared instances disappear from other peers; other hosts manage their own objects. This does not remove residents, avatars or inference models.

Remembered people and places

Tell an owned resident “Remember this as our meeting spot.” It can name the speaker’s observed position at that message, then use “Take me back to our meeting spot” as a normal spatial objective, including after reload. The model chooses a grounded anchor; it cannot supply arbitrary coordinates. Movement rechecks the walking surface, obstacles and range and confirms arrival through the motor. A saved location is not a guarantee that it remains reachable. The name must appear in your message. Naming a place cannot overwrite an existing destination; use a different name for a different point.

Open ☰ → Residents → Mind beside Edit to inspect remembered places and identity-based encounters, correct a label/note or forget an entry. Corrections are owner reports, not newly observed facts. Last-seen positions are historical. People are matched by authenticated peer identity, never by display name; a returning visitor with a new peer identity remains a separate encounter. Forget removes the knowledge entry and blocks delayed recreation; original conversation history and already-saved movement tasks remain separate.

Knowledge stays in this device’s IndexedDB, scoped by resident, world and conversation. Public speech can use public knowledge; private knowledge and reflections informed by it stay out of public-speaking cycles. Clones inherit knowledge only under the existing history/private-history sharing choices. Shared modules provide durable evidence, bounded recall, model admission and Mind controls; world adapters continue to own sensing and movement. This is memory-guided adaptation, not neural weight training or a global world map. The complete remember/reload/return workflow was verified using peer-hosted Nemotron Nano4B and the learned WebGPU motor. Task status and physical receipts establish movement; conversational coordinates or promises can still be wrong. Small models can miss an action or copy an example: the 0.8B Qwen test did not reliably follow this workflow. Storage guards reject invented names and replacement destinations. Forgetting retains a small tombstone to prevent delayed recreation; the bounded store currently allows 256 records per resident/world, including those tombstones.

Run npm run test:resident-knowledge from the repository root for the focused store, native IndexedDB, clone-profile, grounded-action and Mind UI checks.

New residents, personal guides and clones default to Self directed movement. With Reflect and pursue goals automatically enabled, their OODA loop chooses when and where to move through the learned motor. They wait when no action is chosen; this profile does not script roaming. Owner chat and saved objectives can still direct movement. Choose a profile in Residents or Edit resident; existing explicit preferences remain saved.

Resident details and troubleshooting

Select a resident in chat and choose Resident, or choose Edit in the Residents list. The dedicated window shows its profile, movement, sharing and autonomy settings, saved task, remembered people/places, model routes and recent activity. It stays available while the resident is thinking. Owner edits preserve identity and history; a stale draft cannot overwrite a newer self-edit. Peer residents expose public information and an optional Clone action.

The Activity tab keeps bounded diagnostic metadata in a separate local IndexedDB journal: room-message receipt, inference routing/failure, publication, OODA recovery and task state. Errors remain visible after automatic recovery. Expand an event for its request/message ID, model/peer and available context-token counts. This is not a transcript, is never model input, and is not cloned or advertised to peers. Existing saved inference failures also appear, so older failures can be inspected before this diagnostic journal has accumulated data.

Room errors appear in Room chat independently of private-conversation status. A provider GPU loss, context overflow and an unavailable model are different failures; inspecting the actual event is more useful than inferring the cause from a pause. Optional public observations are bounded to leave more room for identity, the current message and the reply. This cannot guarantee that every personality fits every model or prevent a model from imitating quoted speech.

Run npm run test:resident-inspector for owner/peer access, revision-safe editing, diagnostic persistence, error attribution and desktop/mobile UI regressions.

You can close chat, move through the world, or switch between Room and residents while a reply is running. It stays with the original conversation; return there to read it. Sending remains serialized. Cancel, removing the resident, or leaving the world stops work explicitly; dismissing a chat only stops microphone capture. Opening model controls during a conversation asks you to wait rather than cancelling the reply.

Owner requests to create world objects are planned and executed before the resident narrates the result. The receipt reports the actual saved CID and position; a later reply failure does not undo a saved object. If rendering fails after saving, the object is reported as saved with a display error. A resident still depends on a compatible reasoning, image and 3D provider for each stage.

Task waiting reasons distinguish busy capacity, recovery and a missing compatible model. Unknown availability remains labeled unknown. The current speaker is identified separately from nearby residents and recalled speech; model-generated repetition can still occur and should not be mistaken for a verified action.

Resizing placed objects

Tell a resident you own “make the castle 10x bigger”, or request an absolute size. The resident selects an existing owned object from its current observations; the host checks the saved revision, available ground and other objects before changing it. Resizing reuses the mesh and requires only language inference, not an image or 3D generator. A verified receipt reports the old and new size. The same object and size survive reload and are shared with current-version peers. If several objects match, identify the target more precisely. An enlargement that crosses the world boundary or overlaps occupied space is rejected, not silently reduced. Objects remain cosmetic rather than new collision bodies.

Omitted sizes now use object-specific defaults: a castle's largest dimension is 96 world units, a house 36, a car 15 and a wrestling ring 24; a cube is 6 units tall. Explicit sizes override those defaults. Existing saved objects retain their size until edited. Object dimensions allow 0.3–1024 units subject to scene clearance; this does not change resident-avatar size limits.

Placed meshes now contact the visible themed ground using sampled support points. Theme changes and resizing update that contact without changing mesh orientation or authoritative world coordinates. This does not flatten an irregular generated base or add terrain-conforming geometry. Refresh both peers to use the new object-transform protocol; older peers omit revisions and sizes they cannot represent.

Remote avatars and placed objects reuse verified artifact connections while loading their mesh blocks. Working providers take priority; an unavailable alternative no longer delays every block. Connection attempts remain bounded even while the viewer stays open. A first transfer still depends on discovery, connection quality and mesh size.

File sharing maintains a separate relay connection from chat. If that connection is lost, it now retries the configured relay automatically, and viewers refresh providers that have no file-transfer address. “No reachable file-transfer address yet” means the host is reconnecting; it does not mean the saved model was deleted. After updating from an older build, refresh the original hosting tab as well as the viewer. The host must remain open unless another peer has retained and shares the object. Peer identity checks and content verification remain required.
